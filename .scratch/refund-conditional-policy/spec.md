# 退款资格判断与按需政策解释改造

Status: ready-for-agent

## 问题

当前流程在订单满足退款条件时仍检索政策，要求模型提取条款结论，并在提交前保存政策核验事件。政策服务不可用、证据不足或模型解释失败可能阻断合格的模拟退款。消费者同时要求办理和询问依据时，流程也需要区分独立的政策咨询与消费者提出的办理条件。

## 方案

程序根据可信订单事实统一判断退款资格。普通查单和合格的资格咨询直接答复，合格且已明确授权的办理调用现有退款服务。程序明确拒绝时，按拒绝原因查找可核验的正式政策。通用政策咨询和消费者明确索要依据时按需求检索。依据不可核实时保留已确认的业务结果。架构决策见 [ADR-0012](../../docs/adr/0012-refund-policy-for-explanation.md)。

## 用户故事

1. 作为消费者，我想查询本人订单的支付、发货或退款状态，以便直接了解当前事实。
2. 作为消费者，我想知道本人订单是否符合退款条件，以便决定是否另行授权办理。
3. 作为消费者，我想在缺少订单号或目标不明确时收到追问，以便确认要查询或办理的订单。
4. 作为等待补号的消费者，我想补充本轮订单号，以便继续原来的退款资格咨询。
5. 作为消费者，我想了解通用退款政策，以便核对适用条款或已发布的常见问题答案。
6. 作为消费者，我想在订单被拒绝时先看到真实的业务原因，以便在政策服务异常时也能了解结果。
7. 作为消费者，我想在有适用条款时看到可核验的来源，以便理解拒绝原因。
8. 作为消费者，我想在明确授权且符合资格时完成模拟退款，以便即使政策服务暂时不可用也能办理。
9. 作为消费者，我想在办理的同时索要政策依据，以便收到实际办理结果和能够核实的说明。
10. 作为消费者，我想先看条款再决定是否退款，以便保留本次授权的决定权。
11. 作为消费者，我想在以查到正式条款为办理条件时先看到经核验的条款，以便随后明确决定是否办理。
12. 作为消费者，我想在提交前订单状态变化时按最新事实得到处理，以便系统只对仍符合条件的订单办理。
13. 作为消费者，我想在订单已经退款时收到原退款回执，以便确认退款编号和金额。
14. 作为消费者，我想在结果待核对时得到明确提示，以便区分已确认的结果和仍待确认的办理。
15. 作为政策维护人员，我想让解释使用正式发布的适用条款，以便从政策目录追溯来源和版本。
16. 作为维护人员，我想区分政策解释失败和退款办理失败，以便准确判断哪个环节需要处理。
17. 作为验收人员，我想观察实际工具调用次数和退款记录，以便验证各条路径的办理和检索行为。
18. 作为演示维护人员，我想切换时从重置后的开发数据和新会话开始，以便直接验证新流程。

## 实现决定

### 业务规则与授权

- 由同一套确定性业务规则判断退款资格。资格咨询、办理前核验和退款提交事务内的最终核验都复用这些规则。保留现有支付、发货、已有退款及订单归属的处理语义和优先级。
- 查单成功且取得可信本人订单事实后才判断资格。订单不可访问、查单失败或状态无法可靠确认时，按相应的查单或业务错误返回。普通状态查询直接根据可信订单信息回答。
- 退款办理授权来自本轮消费者消息。该消息须明确要求办理，并写出唯一目标订单号。缺号、只指代历史订单或同时指定多笔订单时，请消费者用一条明确指令重新指定。资格咨询补号仍接续只读咨询。
- “符合退款条件就帮我退”可以按既有授权规则核验。“帮我退，并告诉我依据”表示办理指令和附带的政策问题。消费者表示要先看条款再决定，或把查到正式条款设为条件时，先回答政策问题，收到下一轮包含唯一订单号的明确办理指令后才能办理。查不到所需的正式条款时，说明依据暂时无法核实并结束本轮。
- 合格且有明确授权时调用现有退款服务。沿用提交记录、幂等、事务、并发控制和退款结果核对机制。锁定后的最终校验使用最新可信状态，退款金额、退款编号和办理结果以业务回执为准。已退款或待核对的办理优先返回原结果或进入核对流程。

### 退款调查与动态重规划

- `INTENT` 识别查询目标、订单号及明确的政策需求。普通 `INTENT` 沿用一次结构化模型调用的验收口径，授权由程序独立核验。
- `PLAN` 对退款资格咨询、办理和普通查单先安排一个查单步骤。通用政策咨询直接安排政策检索。`EXECUTE` 执行当前步骤，`OBSERVE` 核验本轮工具回执和订单事实。
- `REPLAN` 按已确认的订单事实调用退款资格规则。合格咨询直接回复，合格办理进入现有业务核验及提交路径。明确的资格拒绝按原因追加一个政策步骤，更新步骤索引并执行该步骤。消费者独立索要特定订单的政策依据时，同样可以追加只读政策调查。
- 事务内已确认的资格拒绝可以在退出事务后按最新的业务拒绝原因解释。解释引用需要更多事实时，使用能确认与拒绝相符的可信事实。系统故障、通信异常以及退款结果待核对分别按业务结果处理。
- 将业务资格结果、退款办理授权、业务核验、政策证据及退款回执作为各自用途明确的数据。进入新一轮时按已有生命周期清理上轮业务状态，接续待补号时保留有权使用的待办。追加政策步骤具备幂等性，补查通过既有预算复用该步骤。开发切换按约定使用新的会话和流程状态。

### 政策证据、回复与发布

- 资格拒绝的首查及补查按程序给出的拒绝原因构造查询，只使用必要的业务信息。检索候选由正式发布目录和本轮政策版本快照确定。沿用出处、原文、版本、适用条件和例外的核验。
- 政策解释模型用于理解证据和解释。业务规则、授权、退款金额及结果取自程序和可信工具回执。回复先给已确认的业务结果，再按需要附上核实的依据。遇到无证据、服务失败或条款不适用时，仍回答已确认的业务事实。
- 发现已检索条款与程序结论矛盾时，记录冲突并给出可核查的说明。矛盾条款不用于支持拒绝，补查预算用于证据不足的适当补查。政策冲突由业务审核及发布流程处理。
- 取消提交前 RAG、政策核验和政策核验事件持久化的门槛。订单服务、提交准备和退款服务在政策后端离线时可用。普通查单和自然语言理解的既有模型依赖按各自路径验收。
- 正式政策 RF-013 新版与应用切换协调生效，保留政策发布目录、版本快照和引用核验。开发环境切换使用现有退款演示数据重置入口并重新装载样例。实际切换时确认目标开发库与生效政策版本。

## 测试决定

优先从现有退款工作流的单轮或多轮入口验证编排、回复、授权和工具调用次数。使用现有工具注入点或事件统计调用，复用隔离 MCP 与 MySQL 的验证入口核对事务、退款记录、并发和结果待核对行为。

| 场景 | 验收结果 |
| --- | --- |
| 通用政策咨询 | 调用政策检索，答复引用经核实的适用依据 |
| 普通状态查询 | 零次政策检索，零次退款提交 |
| 合格的退款资格咨询 | 零次政策检索，零次退款提交 |
| 合格且已授权的普通办理 | 零次政策检索，首次办理一次有效提交，回复实际回执 |
| 首次查单或提交前复核明确拒绝 | 零次退款提交，按业务原因追加一个政策步骤，检索受预算约束 |
| 提交事务读取到最新状态并拒绝 | 一次退款服务调用，零条新退款记录，按已确认的拒绝原因回复 |
| 找不到或无法访问订单、查单工具失败 | 按查单结果处理，零次退款提交，政策检索不替代本人订单事实 |
| 附带索要依据和等待条款后再授权 | 分别验证办理结果与解释降级，以及后续含订单号的明确授权生效 |
| 正式条款是消费者的办理条件 | 出示已核实条款后等待之后含订单号的明确办理指令，无法核实时结束本轮 |
| 政策无证据、回执异常、条款冲突或提示注入 | 保留业务结论，引用仅使用有效且适用的证据，补查有界 |
| 政策组件不可用 | 从冷启动覆盖正常业务；合格且已授权可办，程序拒绝仍可答复真实原因 |
| 重复提交、已退款、结果不明、并发、事务失败 | 核对实际业务记录及结果；禁止重复退款、盲目重发和错误宣称成功 |
| 新会话补号、工作流恢复与开发切换 | 验证只读补号接续、步骤恢复不重复追加、旧授权不自动生效，以及重置后新会话可用 |

资格判断使用现有可信事实，验收其模型调用计数为零。保留普通 `INTENT` 一次调用、缺号停在计划前和歧义零误授权等共享回归。运行完整项目测试和适用的代码质量检查，并在隔离环境验证业务集成。

[订单号提取工单 02](../order-id-extraction/issues/02-verify-qwen-extraction-live.md) 继续用工单 01 固定基线完成独立实模对照，按各自退款流程版本记录指标。它的已知错例、独立样本和提取验收门槛作为该工单的交付。这里验证新流程对订单号来源、授权和只读补号契约的回归。

## 范围边界

- 本项目范围为模拟退款。真实支付接入、部分退款、新退款渠道和新的业务资格条件均在范围之外。
- 订单号提取修复、工单 02 的关闭、旧 Checkpoint 迁移、生产数据清理、单独的退款审计系统、规则引擎及政策发布管理平台分别沿既有项目边界处理。
