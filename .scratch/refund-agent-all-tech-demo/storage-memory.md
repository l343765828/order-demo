# 退款 Agent：Milvus、MySQL 与记忆边界

日期：2026-11-18  
性质：已纳入 2026-11-19 用户确认的设计基线，退款应用持久化尚未实施  
关联：[主设计](spec.md)、[ADR-0004](../../docs/adr/0004-refund-agent-storage-boundaries.md)、根 [GLOSSARY.md](../../GLOSSARY.md)

## 1. 本轮已明确的方向

- 用户明确要求将向量存入集群已有 Milvus；RAG 不再采用进程内向量索引作为实际存储和检索后端。
- 原始聊天、退款会话记忆与消费者跨会话记忆使用 MySQL 持久化；原始聊天完整保存，不再按纯内存方案设计。
- 用户确认长期记忆只保存消费者明确要求记住的稳定偏好，不自动将全部聊天提炼为长期事实，退款办理授权不跨会话继承。
- 用户确认模拟订单与退款记录也存入 MySQL，跨重启重复申请仍返回原退款记录。
- 用户确认自动上下文压缩与失败时暂停的边界；支持在聊天中查看、更正和删除长期偏好，同类偏好采用最新明确指令。
- 不因为使用数据库就自动扩大业务范围：仍是模拟订单、模拟退款和消费者 CLI 对话，不接入真实支付。
- “短期”指当前会话范围，“长期”指跨会话复用范围；不能将短期记忆等同于只保存在 RAM，也不能将所有已保存聊天等同于已经形成长期记忆。

用户已确认正常重启保留聊天、会话与业务记录，只有显式执行演示重置操作才恢复初始数据。该决定替代此前 Q16 的“重启自动恢复初始演示数据”；MySQL 和 Milvus 均不按应用启动事件自动清空。

## 2. 数据职责

| 数据 | 存储方向 | 读取范围与用途 | 当前决定状态 |
| --- | --- | --- | --- |

长期记忆若后续确实需要语义检索，其原始内容仍可由 MySQL 管理，衍生向量写入 Milvus 并与政策向量隔离；本轮尚未决定为消费者记忆新增向量检索，不提前增加这条写入链路。

## 3. 短期记忆、聊天记录与长期记忆的区别

“我要退款 → 请提供订单号 → DEMO-1001”使用同会话历史与待办状态完成补单，属于退款会话记忆。即使这些内容保存在 MySQL，仍然是短期、会话内记忆。

将三条消息保存到聊天表，只是留下原始会话记录；消费者跨会话记忆则按已确认规则，只接受消费者明确要求记住的稳定偏好。例如“请记住，我希望用中文简短回答”属于允许形成长期记忆的范围；一般退款聊天和模型自动总结不因此进入长期记忆。用户已确认可在聊天中查看、更正和删除偏好，同类偏好采用最新明确指令。

退款办理授权只适用于指定消费者和指定订单的当前办理过程，不因归档聊天或产生长期记忆而变成未来订单的授权。订单支付状态、发货状态与退款结果仍由业务数据查询提供；不能以历史聊天陈述或记忆摘要代替。

## 4. LangGraph 的接入边界

短期会话记忆需要保存可恢复的图状态，不能只新增聊天消息表就宣称已接入 checkpointer。框架的 checkpointer 与跨会话 store 是两个职责：前者按 thread 保存图状态，后者保存应用定义的跨 thread 信息；二者可以使用同一 MySQL 实例，但数据模型和读取范围分别设计。

已查到第三方 `langgraph-checkpoint-mysql` 实现，它不属于 LangGraph 核心内置 MySQL 组件。实施前需要核对目标 MySQL 版本、当前 LangGraph / DeepAgent 版本、同步或异步调用方式及所需接口，完成真实读写与恢复验证；不在本轮设计中直接锁定适配器或宣称兼容已通过。

把 checkpoint 保存到 MySQL 不自动解决退款幂等，也不代表允许重放退款写入。已确认重启保留后，恢复会话须重查订单与退款记录，业务唯一约束应跨重启有效；已保存的授权和旧工具观察不能绕过执行前复核。原始消息归档与模型本轮输入分别管理，完整留库不表示每次把全部历史发送给模型。

MySQL 提交阶段如果出现连接中断或回执丢失，按唯一业务标识核对原退款记录。确认成功后返回原结果。暂时查无结果则标记待核对，并拦截所有会话对同一订单的新提交。确认旧提交未产生退款且已关闭后，原会话可凭消费者的明确继续指令恢复待办，新会话可凭明确指定订单的办理指令发起新申请。

## 5. Milvus 的接入边界

政策 Markdown → 条款分块 → 已选 BGE-M3 服务生成向量 → 写入退款政策专用 collection → query 向量检索 → BGE reranker 重排 → 返回条款与引用元数据。

用户确认专用 collection `order_demo_refund_policy` 的八个字段。所有字段必填，字符串长度按 UTF-8 字节计，保留完整条款和 FAQ 问答。

| 字段 | 类型 | 用途 |
| --- | --- | --- |
| `chunk_id` | `VARCHAR(64)` 主键，`auto_id=false` | 文档编号、版本和条目编号的规范化组合经 SHA-256 得到固定标识，重复入库可定位同一行。 |
| `document_id` | `VARCHAR(64)` | 文档编号，当前为 `DEMO-REFUND-POLICY`。 |
| `title` | `VARCHAR(256)` | 文档标题，用于展示来源。 |
| `version` | `VARCHAR(32)` | 文档版本，查询限定当前发布版本。 |
| `clause_id` | `VARCHAR(32)` | 条目编号，如 `RF-003`、`FAQ-001`。 |
| `entry_type` | `VARCHAR(16)` | `policy` 为正式条款，`faq` 为问答，用于检索过滤。 |
| `text` | `VARCHAR(4096)` | 完整条款或 FAQ 的问题与答案，供重排和证据核验。 |
| `embedding` | `FLOAT_VECTOR(1024)` | BGE-M3 编码的 L2 归一化向量，使用 `FLAT` 索引和 `IP` 相似度。 |

FAQ 的政策依据在查询时核验。政策版本更新通过独立入库流程完成，在线只搜索已发布版本；历史版本留存以支持引用追溯。具体发布切换与集群兼容性实施前核实。

客户端可做必要的归一化和结果核验，实际检索后端为 Milvus。Milvus 连接失败或无充分政策证据时沿用已确认规则，停止办理并说明原因，不回退到内存检索绕过该要求。

## 6. 已确认决定与跨服务执行边界

用户已同意本轮 Q1–Q7：只记显式稳定偏好、正常重启保留数据、订单与退款记录使用 MySQL、自动压缩策略、长期偏好管理、重启后的受控恢复和演示重置范围。上述决定已同步主设计、ADR-0004 与 ADR-0005。

### 6.1 长期偏好管理的执行边界

查看只返回当前消费者的有效偏好；更正同类偏好采用消费者最新明确指令；删除后该偏好不再参与后续上下文。消息归档仍完整保存，查看偏好不等同于查看全部聊天，“忘记偏好”也不自动删除原始聊天或业务记录。

旧摘要、旧 checkpoint 与历史原文不能恢复已经删除的偏好或覆盖新值。生成上下文时从当前偏好服务读取有效状态，语义删除或版本标记的具体实现留给实现者，不把旧文字重新当作消费者发出的当前指令。

偏好操作经意图节点解析为具名命令，由固定应用节点访问 MySQL，消费者身份取可信运行上下文。只有实际持久化成功才能回复“已记住”“已更改”或“已忘记”；失败如实说明。调查用 DeepAgent / 子 Agent 不因此获得任意记忆写入、SQL 或退款工具权限。

偏好只影响允许的个性化表达，不改变退款资格、金额、目标订单、政策依据或办理授权。本轮临时表达要求可以优先影响本次回答，但不会隐式覆盖持久化偏好。第一版偏好键与字段、组合指令的解析形式由实现者在该边界内确定，不扩大为任意用户事实的自动记忆。

### 6.2 已确认的恢复与重置

- 重启后只恢复历史与待办，不自动继续未完成退款；消费者明确继续后重新查单、检索政策并核验执行条件，已有成功记录则直接返回原结果。checkpoint 恢复不能自动重放写入节点，重连工具服务也不能触发写入重试。
- 显式演示重置仅重置本演示的聊天、摘要、偏好和模拟业务数据，并重新装载初始订单；保留 Milvus 政策索引，不触及其他演示数据。政策更新使用单独的文档入库流程，重置操作不注册为消费者对话或调查工具。

上述两项已获用户确认。长期偏好目前只需按消费者与偏好类型读取，无已确认的跨偏好语义检索需求，不主动新增向量化链路；具体压缩参数与适配器选择属于实现细节。用户进一步确认[MCP 接入设计](mcp-integration.md)：退款 Agent 直接管理聊天、摘要、偏好和检查点，订单、退款记录及政策检索由独立 MCP 服务负责。

### 6.3 跨服务授权和数据所有权

Host 在当前会话维护消费者明确表达的办理意图。固定节点准备发送时，将本次授权证据保存到 MySQL 提交记录。MCP 服务在退款事务内锁定该提交，核对消费者、订单和授权是否已撤销，并负责写入退款结果。两端的数据职责通过固定应用逻辑实施，首版移除按表授权及独立服务数据库账号的要求。见 [ADR-0008](../../docs/adr/0008-refund-authorization-per-dispatch.md)。

Host 发起新的退款提交前，先确认最终政策核验事件已持久写入结构化日志，再保存带同一 `trace_id` 和幂等键的提交记录。保存失败或无法确认时暂停本次新提交。其他过程事件用于诊断，查单、查看已有退款结果和核对旧提交照常进行。字段和写入顺序见[数据库表结构](database-design.md)。
