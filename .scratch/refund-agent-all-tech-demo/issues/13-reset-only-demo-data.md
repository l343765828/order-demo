# 13: 停流并安全重置演示 MySQL 数据与 checkpoint

**Status:** ready-for-agent

**Blocked by:** [10 维护关闭与恢复](10-close-dispatch-and-resume-refund.md)、[12 长会话压缩](12-compress-long-conversations.md)。

## 目标

维护人员显式执行重置后，演示恢复到初始订单和示例退款状态。本演示旧会话无法恢复，旧请求无法在种子重装后补写，政策知识仍可正常检索。

## 范围

交付两个进程共同遵守的停流、在途写入排空与演示维护入口。清理隔离在 `order_demo` 的会话及模拟业务数据和本演示 checkpoint，重装 01 定义的种子。独立保留 MySQL 政策发布目录及 Milvus 政策集合。

## 涉及的契约

- 在暂停新的演示业务请求后确认在途写入已结束。无法确认时停止重置。先清理 `refund_dispatches`，再按外键依赖清理其关联数据，退款先于订单、摘要先于原文、原文先于会话。清理偏好、本演示线程及相关框架记录后，再装载初始数据。
- 正常进程启动和消费者指令不能触发重置。Milvus 政策、其他演示的数据库及 checkpoint 不在维护边界内。 [数据库设计](../database-design.md) · [MCP 接入](../mcp-integration.md#8-故障重启和重置) · [ADR-0004](../../../docs/adr/0004-refund-agent-storage-boundaries.md)

## 验收标准

- [ ] 先制造真实退款、未决提交、聊天、摘要、偏好和 checkpoint。停流并完成显式重置后，仅恢复五笔初始订单及示例退款，旧会话与线程无法恢复。运行后用同一 CLI 可重新开始演示。
- [ ] 在 Host 和 MCP Server 上设置在途写入及迟到请求，排空无法证明时无清理发生；可以安全排空时才清理，旧请求不能写到已重装种子。重置中新增业务请求受控，不出现半初始化状态下的办理。
- [ ] 重置前后比对 MySQL 政策发布目录的生效版本、目录修订与发布记录，以及 Milvus 本演示政策的文档、版本和行数，并用同一查询检索。另比对其他演示的验收哨兵数据。普通重启保留数据，重复执行显式重置仍得到相同初始种子。
- [ ] 中断一次清理或重装，验证业务流量在数据未恢复一致时保持暂停，按维护指引重试可得到完整初始状态。消费者 CLI、调查工具与普通服务启动都无法启动重置。

## 验证方式

在经批准的隔离验收环境运行重置脚本，事前事后核对七张演示应用表、框架线程、MySQL 政策发布目录、Milvus 候选来源与外部哨兵。用在途屏障和故障注入检查停流，在重置完成后恢复请求验证首个查单及正常办理。
