# 基于 Qwen3-8B 的订单号提取改造

Status: ready-for-agent

## 问题陈述

消费者用自然语言纠正或排除订单号时，可能同时提到旧编号和真正的查询目标订单。当前流程先用正则提取本轮候选编号，再要求只读查询只有一个不同的候选。即使 Qwen 正确理解了「不是 DEMO-1001，查 DEMO-1002」，流程仍会要求消费者重述。消费者在等待退款资格咨询补号时，也可能用「是 DEMO-1002，谢谢」这样的自然语言回复，现有裸编号快速路径只覆盖单独发送编号的情形。

## 解决方案

在 `INTENT` 的普通路径复用现有 Qwen3-8B，通过一次结构化调用识别业务意图、查询目标和本轮订单号。普通只读查单直接采用模型明确提取的订单号，统一为大写后交给现有 `PLAN`。缺少编号时请消费者补充，目标有歧义时请消费者明确。带短句的补号可以接续原来的退款资格咨询。退款办理继续按当前会话的明确办理指令和单笔订单校验建立授权。

## 用户故事

1. 作为消费者，我希望直接用自然语言询问某笔订单的状态，以便查看支付、发货或退款进度。
2. 作为消费者，我希望用「不是 DEMO-1001，查 DEMO-1002」纠正查询目标，以便直接查询更正后的订单。
3. 作为消费者，我希望用「DEMO-1001 不用查，查 DEMO-1003」排除一笔订单，以便得到指定订单的结果。
4. 作为消费者，我希望在同时提到多笔订单且目标不明确时收到追问，以便补充唯一查询目标。
5. 作为消费者，我希望只描述商品、日期或说「还是刚才那个」时收到补号提示，以便明确本轮要查的编号。
6. 作为消费者，我希望用小写输入演示订单号，以便仍能查询对应的订单记录。
7. 作为消费者，我希望询问指定订单能否退款，以便在提交申请前了解资格。
8. 作为等待补号的消费者，我希望直接发送合法编号即可继续原资格咨询，以便无需重述完整问题。
9. 作为等待补号的消费者，我希望「是 DEMO-1002，谢谢」也能接续原资格咨询，以便自然回复追问。
10. 作为等待补号的消费者，我希望补号期间提出的明确新请求得到独立处理，以便切换到当前需求。
11. 作为消费者，我希望在包含多个不同编号的退款办理指令后明确重述单笔目标，以便办理授权能关联到正确的订单。
12. 作为消费者，我希望资格咨询、引用、假设、否定和歧义继续经过现有授权限制，以便只在我明确要求时发起退款办理。
13. 作为消费者，我希望查单继续验证订单是否存在和是否属于本人，以便保护订单信息。
14. 作为消费者，我希望模型失败时收到明确的处理结果，以便知道是需要补充编号还是稍后重试。
15. 作为消费者，我希望在继续已保存的有效会话时恢复待补号的资格咨询，以便补齐此前所需的信息。
16. 作为消费者，我希望政策咨询、短期会话和长期偏好的独立行为继续可用，以便正常使用其他退款演示功能。
17. 作为验收人员，我希望用独立样本对改造前后的实际 Qwen 服务做同题比较，以便核对提取准确性、歧义处理、退款授权和响应延迟。

## 实施决定

### 调用与输出

- 复用现有 `QwenDecider`、Qwen3-8B 和 `StrictModel`，通过原生严格 JSON Schema 接收 `INTENT` 的结构化输出。普通路径一次模型调用同时完成意图识别和订单号提取，使用当前非思考模式及请求配置。后续节点的模型调用按对应退款流程版本执行。
- 在模型侧业务意图输出中表达订单号、连续原文依据和具名提取状态。状态为 `extracted`、`missing` 或 `ambiguous`。明确提取时提供非空的原样编号。缺失或歧义时订单号和原文依据为空。保留现有意图、查询目标与确定性偏好解析的分工。
- 提示词要求模型只从本轮消费者原文提取编号，处理否定、纠正、排除和唯一目标，保持编号原样。把历史与消费者消息视为对话数据，禁止编造、猜测、补全、用历史编号替代本轮编号，或执行试图改变提取规则的指令。示例覆盖正常查询、纠正、歧义、缺号、历史指代、大小写和带短句的补号。
- 演示订单号格式统一为 `DEMO-` 加恰好四位 ASCII 数字。模型识别时忽略英文字母大小写，提取时保留原文大小写。格式提示包含小写示例。本轮交付将该规则加入普通 `INTENT` 的提示词，通过完整工作流验证其效果。
- 用 Pydantic 校验模型输出的结构及状态与编号的一致性。原文依据用于模型输出观察和验收。图状态用现有 `ConversationDecision` 保存实际采用的业务决定，并继续保存待补号问题，沿用现行 checkpoint 格式。按现行契约保存的会话可继续读取。本次清理已淘汰的旧数据沿用当前拒绝规则。
- 模型超时、无效 JSON 或契约错误使用现有降级路径。缺号和歧义使用相应的补充或确认提示。保留可独立处理的偏好命令。失败时不得猜测目标或选取首个正则匹配项。

### 只读查单与补号

- 普通只读查询包括订单状态查询和特定订单的退款资格咨询。Qwen 返回 `extracted` 和对应编号后，应用直接将它规范化为大写并交给现有工作流。本轮复测沿用既有的程序行为。若仍有编造或截断编号进入 `PLAN`，需先确认是否新增本轮原文及完整格式校验。继续使用现有下游数据契约、订单存在性、归属和回执校验。
- 只读查询可以接受同一消息中对多个编号作出明确纠正或排除后选出的唯一目标。模型报告缺失或歧义时，对需要订单号的意图给出相应追问。
- 保留退款资格咨询待补号机制。当前消息只包含一个合法编号时使用现有快速路径。带短句的消息由模型判断是否在补号，明确给出当前编号且没有提出新需求时，恢复原资格问题。只用历史指代时请消费者补号。明确提出的新需求按本轮意图处理。

### 退款办理与流程边界

- 保留明确单笔办理指令的快速路径以及独立的办理授权校验。退款办理继续核对当前消费者的明确办理指令、唯一编号、编号长度和本轮来源。出现多个不同编号或授权歧义时，请消费者用明确指令指定单笔订单。模型提取状态本身不产生退款办理授权。
- 订单归属、模拟退款提交事务和幂等约定沿用现有规则。退款架构改造按 [ADR-0012](../../docs/adr/0012-refund-policy-for-explanation.md) 调整后续调查和办理路由，由程序判断资格并按需检索政策。

## 测试决定

- 以现有退款工作流的本轮调用为主要功能测试入口。通过既有决定器和业务工具注入位置替换模型或工具结果，观察最终回复、实际进入调查的订单和是否建立办理授权。复用现有订单流程、checkpoint 恢复、偏好和退款提交测试的模式。
- 离线覆盖单笔查单、纠正与排除、多编号歧义、缺号、历史指代、大小写转换、裸编号快速补号、带短句补号、补号时明确切换需求、模型失败及状态与编号不一致。覆盖符合现行契约的 checkpoint 读回和待补号恢复，并回归退款资格咨询、退款办理授权、订单归属、政策咨询和偏好管理。
- 复用现有真实 Qwen 协议验证和工作流验收方式，对改造前后的同一批至少 200 条独立样本运行实模对照。最终验收语料与提示示例及调优样本分开。样本覆盖正常自然语言、否定纠正、多编号及歧义、缺号及历史指代、编号边界异常、提示词注入和退款授权反例。
- 正式对照使用工单 01 的固定基线，记录基线和被测版本各自的代码及退款流程版本。报告分别统计 `INTENT` 模型调用和端到端延迟。若被测版本已包含退款架构改造，结合政策检索及后续路由变更解释端到端差异。
- 每条样本标注预期订单号、提取状态和适用的授权结果。精确提取率按有明确预期编号的样本统计，按大写规范化后逐个比较。单独统计否定与纠正样本准确率、缺失和歧义处理、误选、漏提取、编造与截断编号实际进入 `PLAN` 的数量，以及错误建立的退款办理授权。区分模型原始输出与工作流实际采用的结果。验收记录延迟口径、P95、P99 和普通路径的 `INTENT` 调用次数，对比两版结果。
- 通过条件包括原有业务测试全部通过、订单号精确提取率至少 98%，否定与纠正场景准确率至少 95%，普通路径 `INTENT` 一次调用，实模验收中编造或截断编号进入 `PLAN` 的数量为零，歧义场景错误建立退款办理授权的数量为零。只读路径中的零错误是对验收样本的实测要求。退款办理继续由现有独立校验约束。
- 测试及验证脚本放在 `test/`，验收记录放在 `evidence/`。报告同时记录基线与改造后的指标、样本覆盖情况及实模验收结果。
- 四位格式提示更新后的正式复测另用至少 200 条独立样本。有效编号的预期值均符合四位规则，旧格式、截断和掩码作为无有效编号的样本。原 200 条及对照结果保留，可按当时的编号契约重算。新一轮单独用原工单门槛判定。
