# 退款政策依据与单币种数据契约

Status: ready-for-agent

## 问题

指定订单的资格解释依赖代码里预设的条款号和解释文案。批准的政策即使只调整条款编号或措辞，检索结果也可能无法用于回复，或者回复仍沿用旧文案。政策审批、代码开发和文档上传由不同人员负责，运营上传时只掌握已批准的政策原文。因订单资格被拒绝的办理请求也需要让消费者看到相关政策依据。

演示金额统一采用人民币分。订单查询结果、退款回执和数据库仍逐笔保存固定的 `currency` 字段，并在业务与 MCP 之间重复传递。删除字段时需要保留现有订单、退款记录和退款会话的可读性。

## 方案

办理代码根据可信订单事实确定退款资格和办理结果。退款调查从本轮生效的政策版本检索候选，回答时由现有 `Qwen/Qwen3-8B` 服务从候选原文提取结构化的适用条件和结论。代码核对订单事实、业务结果和原始检索回执，取得依据后回复办理结论、相关政策原文和出处。实际办理因资格被拒绝时也执行这项只读调查。

订单和退款的数据契约直接使用整数人民币分，移除应用模型、MCP 结果及相关数据库表中的 `currency`。升级时验证旧金额的币种，并让旧会话仍可读取和恢复。

## 用户故事

1. 作为消费者，我想询问本人订单是否符合退款条件，以便决定是否另行提出退款办理授权。
2. 作为消费者，我想在资格答复里同时看到办理结论、相关政策原文和出处，以便核对系统为什么得出这个结果。
3. 作为未支付订单的消费者，我想看到适用于未支付订单的政策依据，以便了解本次拒绝的原因。
4. 作为已发货订单的消费者，我想在明确提出退款后看到办理结果和发货条件对应的条款，以便理解为什么未提交退款。
5. 作为已完成模拟退款的消费者，我想查询原退款结果，以便确认原金额和退款单号。
6. 作为消费者，我想在政策检索失败或依据不足时仍了解已经确认的订单事实和办理结果，以便区分订单状态与政策核验状态。
7. 作为消费者，我想在政策与办理规则冲突时收到说明，以便知道为什么本次没有提交新的退款。
8. 作为消费者，我想在一次退款调查的多次检索中看到同一政策版本的依据，以便引用能反映一次完整退款调查。
9. 作为消费者，我想在应用升级后继续读取已有退款会话和历史结果，以便延续原来的退款办理恢复流程。
10. 作为消费者，我想继续按人民币理解订单金额和模拟退款金额，以便清楚比较实付和退款金额。
11. 作为政策审批人员，我想以审批通过的政策原文作为引用来源，以便消费者看到实际生效的内容。
12. 作为运营人员，我想上传已审批的政策原文，由系统完成切分和查找，以便按现有职责发布政策。
13. 作为开发人员，我想在办理代码里依赖明确的订单事实和业务规则，以便按既定开发流程实现和验收资格变化。
14. 作为开发人员，我想让条款编号和解释由检索结果提供，以便条款改号或调整表述后能够直接引用新版内容。
15. 作为维护人员，我想在新退款提交前查到实际采用的政策文档、版本、条款和检索事件，以便追溯办理决定。
16. 作为维护人员，我想从业务模型、MCP 返回结果和数据库中移除重复的单币种字段，以便简化阅读和跨层维护。
17. 作为维护人员，我想在迁移前核对历史币种，并在升级后保留历史金额和会话信息，以便避免误解旧金额或丢失退款进度。

## 实现决定

### 政策发布、订单资格和模型职责

- 政策经审批后由运营上传原文，由开发实现配套办理规则。程序自动从原文提取用于引用的条款编号并建立检索索引。
- 办理资格变化时，配套政策和办理代码一起验收和协调上线，确保政策生效时对应办理规则已可用。MCP 继续管理政策发布目录，退款调查沿用本轮政策版本快照。
- 办理代码根据四项可信事实作出确定性的资格判断，分别是订单归属、支付状态、发货状态和已有模拟退款记录。订单归属以本人订单的查询结果为准。资格咨询与退款办理授权仍按各自契约处理。
- 按问题、已确认的订单事实或业务原因检索本轮生效政策，按候选的实际含义寻找依据。采用依据的判断从代码中移除固定条款号、固定政策文案及针对已知政策正文的预置摘要匹配。发布完整性和回执来源的校验继续使用原有机制。
- 在本轮检索后、答复或提交新退款前，对本次候选条款调用现有模型，按结构化契约提取适用条件、限定或例外、政策结论以及在原文中的位置或摘录。候选正文是待理解的资料。办理代码使用已知事实和固定业务取值核对提取结果，逐项保留适用条件的关系。
- 当条件无法用本次支持的订单事实表达或核实、提取失败或缺少明确结论时，该候选不能成为充分依据。可办理的政策依据须支持整单原路退款。候选适用于订单但政策结论与办理结果冲突时，说明冲突。引用必须对应本轮检索回执中的实际正式条款，包含真实文档、版本、条款和原文出处。

### 答复与退款提交

- 资格答复采用办理结论、相关政策原文和出处。直接摘录包含适用条件和结论的相关原文，无需额外调用模型改写。代码可以使用通用结果措辞和已核验的订单事实组织回复。
- 明确要求办理而被资格规则拒绝时，也执行只读政策检索。找到依据后按同样格式答复。依据不足或检索失败时，将已确认的订单事实、未提交退款的结果和无法核实条款的情况如实告知。
- 资格咨询缺少充分依据时，说明已经核实的订单事实及依据不足的情况。依据不足或政策与办理规则冲突时暂停新的退款提交。依据充分时，新的退款提交仍须具备当前消费者的有效办理授权，并确认最终政策核验事件已持久保存。
- 已有退款记录可按原业务结果返回，退款结果核对依据真实业务记录。政策检索失败或资格咨询本身都不会触发新的退款提交。

### 人民币金额与兼容性

- 移除订单与退款的业务模型、查单与退款 MCP 结果、数据库订单及退款表、相关读写和种子数据中的 `currency`。保留 `paid_amount_fen` 和 `amount_fen` 的既有人民币分含义，面向消费者的金额沿用人民币展示。
- 迁移现有数据库时先核对相关历史币种均为人民币。发现异常值时停止该次删列并报告，由维护人员核实。迁移保留订单、退款标识、金额及已确认的办理数据。
- Agent 与 MCP 配套升级，避免旧调用方按旧契约读取已移除字段的响应。旧会话快照在恢复时兼容历史 `currency`，覆盖工具事件、调查观察、订单结果和退款回执等已持久化的形态。新版响应与新写入的快照使用无币种字段的契约。

## 验收决定

优先沿用现有的退款 CLI 联验、MCP 协议验收、退款提交与历史会话恢复验收。从消费者回复、工具返回和数据库实际结果判断行为。模型提取的边界场景可用受控回执稳定覆盖，并用真实的 `Qwen3-8B` 对代表性中文条款验证提取效果。验收至少覆盖以下场景。

- **政策检索与引用。** 同一规则在新版中改号或改写表述后，资格回复引用新版的真实条款号和原文。语义相近但适用条件不同的候选不能被误用。一轮调查中的补查继续使用同一政策版本快照。
- **条件和例外。** 覆盖支付、发货、退款状态和本人归属；明确验证模型保留「仅限」「除外」等条件。缺少相关事实、出现不支持的条件或结构化提取失败时，回复说明依据不足。
- **业务边界。** 资格咨询产生零次退款提交。明确办理且资格被拒时，检索成功则附上真实条款，检索失败仍说明已确认事实和未提交结果。对于拟发起的新退款提交，政策冲突、依据不足或最终核验事件未确认持久化时均不能发起提交。符合条件时验证最终政策依据可追溯，且正常授权办理仍只产生一笔模拟退款。
- **MCP 与数据库。** 查单、退款结果核对和已授权模拟退款的新版结果均无 `currency`。数据库迁移后保留原订单和退款的标识、金额与关联。预迁移发现非人民币数据时，中止删列并保留现有数据。
- **旧会话恢复。** 使用实际包含历史币种字段的会话快照验证读取、进图以及消费者明确继续后的办理恢复。检查原订单和退款金额正确，新写入的会话状态不再携带币种字段。

## 范围

本次沿用既有演示退款资格规则和人民币金额单位。新增退款门槛、多币种支持和发布时预提取模型结果均在本次范围之外。运营流程采用已审批的政策原文。
